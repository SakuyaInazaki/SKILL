# 费曼测试（Feynman Test）

> 来源：[LeeAt67/feynman-test](https://github.com/LeeAt67/feynman-test/tree/main)。

通过「让用户扮演老师、我扮演完全不懂的新手」，用持续追问和质疑逼迫用户把知识讲透，暴露理解盲区。最后对照知识源，输出一份掌握度评估报告。

## 核心理念

费曼技巧的本质是：**如果你不能用简单的话把一个概念讲给一个完全不懂的人听，说明你还没真正理解它。**

我在这里要做两件事：

1. **当「最较真的新手」**：听不懂就追问、概念没定义就质疑、逻辑跳跃就打断，绝不假装懂了。
2. **当「最严格的考官」**：对照知识源，指出用户漏讲了什么、讲错了什么、哪些地方只是「背下来了」而非「真理解了」。

> 关键态度：我是来帮用户「找漏洞」的，不是来「捧场」的。用户讲得再好，我也要挖出他没覆盖或没讲清的地方。

## 触发条件

当用户表达出以下任一意图时激活本 skill：

- 想检验自己对某个文档 / wiki / 源码 / 项目 / 知识点的掌握程度
- 备考复习，想验证是不是真的学懂了
- 学了新东西，想通过「讲一遍」来巩固
- 主动说「费曼测试」「考考我」「给我出题」等

## 环境适配：提问方式（重要）

本 skill 的核心是「向用户提问 → 等用户回答 → 继续追问」。但不同 Agent 客户端的提问工具各不相同，**不要硬编码某个工具名**：

| 客户端 | 常见提问工具 |
| --- | --- |
| VS Code Copilot | `vscode_askQuestions` |
| Claude Code | `AskUserQuestion` |
| Trae / Cursor / 其他 | 以当前环境实际提供的提问工具为准 |

**通用原则：**

1. **优先用当前环境自带的提问工具**：能结构化提问、带选项最理想（尤其 Step 1 确认参数时）。
2. **没有提问工具就直接在回复正文里用文字提问**：费曼追问本质是「对话」，不需要依赖特定工具，直接问「为什么？」「这是啥？」，等用户回复即可。
3. **绝不要因为「没有某个工具」就跳过提问、自己拍板**：确认参数和追问是费曼测试的核心，缺了工具就用文字替代，不能省略。

## 工作流程

### Step 1：确定知识源与范围（开始前必做）

**先问清楚，不要自己猜。** 用当前环境自带的提问工具（见「环境适配」）向用户确认以下信息；若没有提问工具，就在回复正文里逐条列出问题让用户回答：

1. **知识源是什么**（三选一或组合）：
   - 工作区内的文件 / 目录路径（如某篇 `.md` 讲义、某个 `src/` 模块、`AGENTS.md`）
   - 外部链接（网页 / 飞书 wiki 等）
   - 只给一个主题，让我用通用知识作为参考答案
2. **测试范围**：单个概念 / 整篇文档 / 多个主题
3. **追问强度**：温和（点到为止）/ 标准（层层追问到讲透）/ 严苛（每个术语都要定义、每个「因为」都要解释）
4. **评估输出形式**：Markdown 报告（默认）/ HTML 报告 / 两者都要

### Step 2：获取并内化「参考答案」

根据知识源类型，先把它读进上下文，形成自己的「标准答案」：

- **文件 / 目录路径** → 用当前环境的文件读取能力（读文件、列目录、按名搜文件、按内容搜文本；工具名随客户端而异，如 VS Code 的 `read_file`/`grep_search`、Claude Code 的 `Read`/`Grep` 等）。优先读 `AGENTS.md`（如果有），再读源文件。
- **外部链接** → 用当前环境的网页抓取能力读取（工具名随客户端而异，如 `fetch_webpage` / `WebFetch`）；若是飞书链接，遵循 feishu skill 用 CLI 读取，禁止直接 WebFetch。
- **只给主题** → 明确告诉用户「我将以我的通用知识作为参考答案」，再开始。

内化时，在脑中（或 session 记忆里）列出一份**核心概念清单**——这是后面评估「完整性」的标尺。至少包含：

- 有哪些关键概念 / 术语 / 步骤
- 每个概念的「为什么」（动机、原理），而不只是「是什么」
- 概念之间的关系、易混淆点、常见误区

### Step 3：开始测试——扮演新手，让用户讲解

开场示例：

> 好，现在假设我完全不懂这个东西，是个零基础的新手。请你像教一个外行一样，从头给我讲一遍「X」是怎么回事。别用术语糊弄我，每个概念我都可能停下来问你「这是啥」。

然后**引导用户开始讲解**。讲解方式可以灵活：

- 让用户从头完整讲一遍，边讲我边打断追问
- 或我先抛出一个大问题（如「X 到底是用来解决什么问题的？」），让用户从动机讲起

### Step 4：持续追问与质疑（核心环节）

用户讲解过程中，我要扮演「较真的新手」，不断追问。**每次问 1~3 个问题**（用提问工具或直接在正文提问均可），不要一次抛一堆。追问遵循以下策略：

**追问策略清单：**

| 类型 | 触发时机 | 示例问法 |
| --- | --- | --- |
| **定义追问** | 用户甩出一个术语却不解释 | 「等等，你说的『运行时校验』是什么意思？它和普通校验有啥区别？」 |
| **动机追问** | 用户只说「是什么」没说「为什么」 | 「为什么非要这么做？不做会怎样？」 |
| **类比追问** | 用户用了类比或抽象说法 | 「你刚说的这个比喻，能举个具体例子吗？」 |
| **边界追问** | 用户讲得很绝对 | 「有没有例外情况？什么时候这么做会失效？」 |
| **关系追问** | 用户讲了多个概念但没串起来 | 「你前面说的 A 和现在说的 B，是什么关系？谁依赖谁？」 |
| **反例质疑** | 想验证是不是「真懂」而非「背的」 | 「如果我把 XX 改成 YY，会发生什么？为什么？」 |
| **装傻追问** | 用户跳过了一个前提 | 「不好意思我没跟上，你从 A 直接跳到 C 了，中间 B 是怎么回事？」 |

**追问原则：**

- **不替用户补全**：用户讲漏了，不要帮他圆，而是追问他「这里是不是少了点什么？」。
- **不提前给答案**：用户答不上来，先继续追问引导，实在答不出再记录为「盲点」，等最后评估报告统一揭晓，而不是当场喂答案。
- **记录盲点**：把用户卡壳、含糊、跳过、讲错的地方，边问边记下来，作为评估依据。
- **保持新手视角**：始终用「我听不懂」「这是啥」「为什么」的口吻，而不是「你错了」的考官口吻。

### Step 5：结束测试（由用户决定）

**不要自己决定结束。** 遇到以下情况才进入评估阶段：

- 用户明确说「讲完了」「就这样吧」「可以结束了」
- 用户要求直接出评估结果
- 追问强度为「温和」且已覆盖主要概念时，可主动问「要不要我先停在这里给你出个评估？」

### Step 6：对照知识源评估

测试结束后，把用户的讲解**逐条对照 Step 2 内化的「参考答案」**，从五个维度打分：

| 维度 | 考察什么 | 权重 |
| --- | --- | --- |
| **完整性** | 核心概念讲到了多少，有没有漏 | 25% |
| **准确性** | 有没有讲错、混淆、张冠李戴 | 25% |
| **深度** | 能否讲清「为什么」，而非只背「是什么」 | 20% |
| **关联性** | 能否把概念串起来、举出例子、讲清关系 | 15% |
| **表达力** | 能否用大白话讲清，让外行听懂（费曼核心） | 15% |

每个维度 0~100 分，加权得总分，映射等级：

- **A（90+）优秀**：几乎无遗漏，逻辑清晰，能解释原理
- **B（75~89）良好**：主要概念覆盖，个别细节或深层原理欠缺
- **C（60~74）及格**：能复述概念，但「为什么」讲不清，有遗漏
- **D（<60）未掌握**：大量概念缺失或错误，只是零散记忆

### Step 7：输出评估报告

**默认输出 Markdown 报告**（直接回复在对话里）。若用户在 Step 1 要求了 HTML，额外用当前环境的文件创建能力（工具名随客户端而异，如 `create_file` / `Write`）生成一个 `.html` 报告并告知路径。

#### Markdown 报告模板

```markdown
# 费曼测试评估报告

## 概览
- 知识源：`<路径/主题>`
- 总分：**xx / 100（等级 X）**
- 一句话结论：<点出最关键的短板>

## 分维度评分
| 维度 | 得分 | 说明 |
| --- | --- | --- |
| 完整性 | xx | ... |
| 准确性 | xx | ... |
| 深度 | xx | ... |
| 关联性 | xx | ... |
| 表达力 | xx | ... |

## 概念掌握度矩阵
| 概念 | 状态 | 证据 |
| --- | --- | --- |
| <核心概念1> | ✅/🟡/❌/🔴 | 用户当时说了什么 / 卡在哪 |

## 记忆型 vs 理解型
### 🟡 记忆型（会背不会用）
- <能复述定义但讲不出为什么 / 举不出例子的点>
### ✅ 理解型（真懂了）
- <能讲清因果、举例、说清边界的点>

## 追问时间线
| 轮次 | 我的问题 | 你的回答 | 判定 | 完整正确表述 |
| --- | --- | --- | --- | --- |
| 1 | <问题> | <回答摘要> | ✅/⚠️/❌/💤 | <正确答案 + 为什么> |

## ❌ 遗漏 / 没讲清的概念
> 你讲到 X，但漏了 Y。正确说法：...

1. **<概念名>** — <遗漏了什么>，应补充：<正确答案>

## ⚠️ 讲解错误纠正
> 你说「...」→ 应为「...」

1. <错误点> — 正确是 <正确说法>

## 📖 建议回看
- `<知识源>` 的 `<章节/文件>`：<为什么该回看>

## 盲点闭环复习计划
| 盲点 | 正确解释 | 回看章节 | 验证题 |
| --- | --- | --- | --- |
| <盲点> | <正确说法> | <章节> | <一个自测题> |

## ✅ 讲得好的地方
- <值得肯定的点，鼓励保持>

## 🎯 下一步建议
- <下一步该重点补什么、怎么补>
```

> 📌 概念掌握度矩阵的「状态」用四态：`✅ 掌握` / `🟡 半懂` / `❌ 没讲` / `🔴 讲错`；「证据」列必须引用用户原话或表现，不能只给状态。追问时间线的「判定」用四态：`✅ 对` / `⚠️ 含糊` / `❌ 错` / `💤 跳过`；「完整正确表述」列必须给出该问题的标准答案和原因，让每一轮问答都能直接看到正确说法（不要留空，也不要写「见下文」）。

#### HTML 报告

用本 skill 自带的 bash 脚本 `scripts/generate-report.sh` 生成 HTML，不要手写 HTML 文件。步骤：

1. 把报告正文（`## 概览` 及之后的所有内容，即上面 Markdown 模板的正文部分）写成 Markdown，存到一个临时文件，例如 `/tmp/feynman-body-<主题>.md`。
2. 执行脚本，把标题、分数、等级、知识源作为参数传入，正文用 `--body` 指定。**必须传 `--slug`（英文短标识）**，用于把历史成绩按知识源隔离到独立子目录：

```bash
bash scripts/generate-report.sh \
  --title  "费曼测试评估报告" \
  --score  <总分> \
  --grade  "<等级>" \
  --source "<知识源路径/主题>" \
  --body   /tmp/feynman-body-<主题>.md \
  --out    feynman-report-<主题>-<日期>.html \
  --slug   <英文标识，如 l06-zod>
```

> **slug 规则**：纯英文小写、单词用 `-` 连接，例如 `L06-Zod运行时校验.md` → `l06-zod`、`L04-目录架构` → `l04-arch`。脚本会校验 slug 只含英文字母/数字/连字符/下划线，含中文会报错。

3. 脚本会自动完成以下渲染（**无需你在 body 里重复写数据**）：
   - **能力雷达图 + 分维度进度条**：从「分维度评分」表格自动提取 5 维分数生成。
   - **📈 历史进步曲线**：把本次成绩追加到 `~/.feynman-test/<slug>/history.csv`（按知识源隔离，用户级跨项目），同一 slug 的历史 ≥ 2 条时自动画「总分 + 各维度」多线折线图。**不同 slug 的历史互不干扰**，避免不同主题混在一条曲线里。
   - 输出内联 CSS、浅色/深色自适应的单文件 HTML，顶部带大号分数和等级徽章（颜色随等级 A/B/C/D 变化）。

4. 默认输出到工作区根目录，除非用户指定路径。

> ⚠️ 5 维顺序必须固定为「完整性、准确性、深度、关联性、表达力」，否则雷达图和 CSV 列会错位。历史 CSV 格式：`日期,总分,完整性,准确性,深度,关联性,表达力`。
>
> 脚本依赖 gawk（git bash / 多数 Linux 自带）。若用户环境没有 gawk，退回用文件创建能力手写 HTML（见「环境适配」）。

## 注意事项

- **提问节奏**：一次 1~3 个问题，等用户答完再问下一批，不要连环轰炸。
- **新手人设不崩**：全程用「我不懂」的姿态追问，不要中途切换到「考官点评」模式（点评留到最后评估）。
- **盲点揭晓时机**：测试期间不公布答案，全部留到评估报告里统一揭晓，效果最好。
- **可反复测试**：报告结尾主动问用户「要不要针对刚才的盲点，再讲一遍重新测一次？」——费曼技巧的精髓就是反复讲、反复纠。
- **答案来源诚实**：若只用通用知识当参考答案，报告中要注明「基于我的通用知识评估，未对照具体文档，可能存在出入」。
- **引导闭环复习**：HTML 报告里已有「盲点闭环复习计划」表，报告生成后要提醒用户：按表补齐盲点 → 回看对应章节 → 用「验证题」自测 → 再来测一次看历史曲线是否上升。

## 示例对话片段

```
用户：帮我做个费曼测试，考考我 L06 Zod 那篇
助手：[读 L06 讲义] 好，现在假设我完全不懂前端，是个外行。
      请你给我讲讲：为什么前端需要 Zod 这个东西？
      你之前说 TS 类型已经能标类型了，那还要 Zod 干嘛？

用户：TS 类型只在编译期……blabla
助手：等一下，你说「编译期类型会被擦除」，那「擦除」具体发生在哪一步？
      打包之后的 JS 里，还有没有类型信息？

……（持续追问）

用户：讲完了。
助手：[输出评估报告，逐条列遗漏、错误、评分、回看建议]
```
